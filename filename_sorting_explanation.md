# File Naming, IDs, and Sorting in SetBuilder

This document explains how the SetBuilder application manages track identities, file naming conventions, and list sorting mechanisms.

## 1. Track Identity and Structure
The application does not use traditional unique database IDs (like UUIDs) for tracks. Instead, the "identity" and sequence of a track are inherently tied to its position within a standard Python list: `self.project.tracks`.

Each track in this list is represented as a dictionary containing its metadata, including two important name-related keys:
*   **`original_name`**: The clean, base name of the track (e.g., `"My Song.mp3"`).
*   **`filename`**: The actual physical file name on the disk, which usually includes a numeric prefix indicating its order (e.g., `"01 - My Song.mp3"`).

## 2. The Import and Naming Process
When you add tracks to the project (`ProjectActions.add_tracks_worker`), the following sequence occurs:

1.  **Name Cleaning**: The app parses the incoming file's name using `ProjectState.clean_name()`. This function uses a regular expression (`r'^[\d\._\-\s]+'`) to strip away any existing leading numbers, dots, dashes, or spaces. This prevents filenames like `"04 - 01 - Track.mp3"` if you import already numbered files.
2.  **Assigning Physical Names**: A new physical `filename` is generated by prepending the track's current sequence number (its length in the list + 1) to the clean `original_name`.
    *   *Code:* `f"{len(self.project.tracks) + 1:02d} - {original_name}"`
3.  **Storage**: The audio file is physically copied or converted into the project's workspace folder using this new `filename`.

## 3. UI Display
In the main interface (`main.py`), the `Treeview` component displays the tracks. 
*   The `#` (Track Number) column is not a hardcoded ID. It is dynamically generated during the UI refresh loop (`refresh_tree`) based on the track's current index in the `self.project.tracks` list (`i + 1`).
*   The `Track Name` column displays the `original_name` (falling back to `filename` if it's missing), ensuring the user doesn't see the numeric prefixes in the list view.

## 4. Sorting and Reordering
Because tracks are just items in a list, sorting and moving them simply involves manipulating their index in the `self.project.tracks` array.

*   **Manual Moving**: When you click the Up/Down move buttons, `ProjectState.shift_track(idx, offset)` is called. This pops the track dictionary from its current index and inserts it at the new target index.
*   **BPM Sorting**: When you click the "Sort" button, `ProjectState.resort_by_bpm()` uses Python's built-in list sorting, keyed to the `'bpm'` property of each track dictionary.

Whenever the list order changes, the UI is refreshed, and the `#` column automatically updates to reflect the new sequential order (1, 2, 3...).

## 5. The Export/Render Process
The internal list order is completely decoupled from the physical file names *until you export or render*. 

During export (`ExportDialog.render_worker`), the application iterates through the currently sorted `self.project.tracks` list. It dynamically generates a fresh filename for every track based on its *final* index in the loop:
*   `new_filename = f"{i + 1:02d} - {original_name}"`

The audio file is then exported, rendered, or renamed in-place to this new sequence name. This ensures that the final audio files in your system folder perfectly match the sorted order you created in the app's UI.

### Summary
*   **ID**: Implicit, based on list index.
*   **Sorting**: Python list manipulation (`pop`/`insert` or `.sort()`).
*   **Display**: Clean names are shown; row numbers are dynamically rendered.
*   **Files**: Physical files are only forced to match the list's sequence upon Import and Export.

## 6. Persistence of Ordering Changes
When you change the order of the tracks (either by moving them manually or using the BPM sort feature), the application saves your progress using the following mechanism:

1.  **Memory Update**: The internal Python list `self.project.tracks` is immediately reordered in memory.
2.  **Dirty Flag**: The application flags the project state as modified by setting `self.project.needs_save = True`.
3.  **Autosave Daemon**: A background thread (`autosave_daemon` in `main.py`) checks this flag every second. When it detects a pending save, it automatically triggers `ProjectState.save_metadata()`.
4.  **JSON Rewrite**: The `save_metadata()` function completely overwrites the `metadata/tracks.json` file. It iterates through the newly ordered `self.project.tracks` list and writes the track dictionaries in that exact sequence. Therefore, the JSON array's natural order acts as the permanent record of your custom sorting.
